# Sentio — Java Backend

`user-service` — автентифікація, користувачі, організації. Видає JWT для решти застосунку (Go-сервіси лише валідують, свого auth не мають).

## Auth-контракт: JWT + JWKS

Цей розділ — контракт між `user-service` (видає токени) і будь-яким сервісом, що їх валідує (Go: `Notifications`, `Registry Monitor` — SEN-33). Формат claims тут фіксується і не змінюється без ревʼю обох сторін.

### Алгоритм і заголовок

- **RS256** (асиметричний). Приватний ключ існує лише в `user-service`, ніде більше не розповсюджується.
- Заголовок токена містить `kid` — ідентифікатор ключа (SHA-256 thumbprint публічного ключа), яким і підписано конкретний токен. Використовується для пошуку правильного публічного ключа в JWKS під час верифікації.

### Claims

| Claim | Тип | Опис |
|---|---|---|
| `sub` | string | ID користувача (те саме значення, що й `id`, у форматі рядка — стандартне поле JWT-специфікації) |
| `id` | number | ID користувача, дублює `sub` числом (зручно для клієнтів, яким не треба парсити рядок) |
| `org_id` | number | ID організації, у контексті якої видано токен — саме та, що позначена `is_default = true` для цього користувача на момент видачі |
| `roles` | string[] | Роль користувача в `org_id` (`OWNER` / `LAWYER` / `ASSISTANT`) + `"ADMIN"`, якщо `platform_role = ADMIN`. `"USER"` (дефолтний platform-рівень) у масив не додається |
| `iss` | string | Видавець токена (`app.jwt.issuer`, зараз `sentio-startup`) |
| `iat` | number | Час видачі (Unix timestamp, секунди) |
| `exp` | number | Час закінчення дії (Unix timestamp, секунди). Access-токен живе 15 хв (`app.jwt.access-token-expiration`) |

Claims поза цим списком (крім `id`, який лишається як зручний аліас `sub`) не додаються навмисно — якщо знадобиться щось нове в контракті, спершу узгодити тут, а тоді вже в коді.

### JWKS-ендпоінт

```text
GET /api/v1/.well-known/jwks.json
```

Публічний, без автентифікації. Повертає стандартний JWK Set (`{"keys": [...]}`) з публічним(и) RSA-ключем(ами).

> **Важливо для клієнтів:** попри конвенцію `/.well-known/*` жити в корені домену, тут шлях іде під `server.servlet.context-path` застосунку (`/api/v1`) — конфігуруйте Go-сторону саме з цим повним шляхом, а не з голим `/.well-known/jwks.json`.

### Ротація ключів

Під час ротації JWKS тимчасово віддає **два** ключі одночасно (поточний + попередній) — токени, видані ще старим ключем, лишаються валідними до природного `exp` (максимум 15 хв), поки старий ключ ще в масиві `keys`. Клієнти мають кешувати JWKS за `kid` і оновлювати кеш, коли зустрічають незнайомий `kid` у токені (а не раз на весь час життя процесу) — саме так і задумано в `lestrrat-go/jwx/v2/jwk` (SEN-33).

### Сервісні виклики

Виклики сервіс-до-сервісу (Go → Java, `document-service` → `case-service`) використовують окремий токен з `roles: ["SERVICE"]`, а не токен користувача.

```text
POST /api/v1/auth/service-token
```

Client-credentials-подібний флоу: тіло запиту — `{ "clientId": "<email службового юзера>", "secret": "<SERVICE_SECRET>" }`. У відповідь — access-токен (той самий формат, що й звичайний, `roles: ["SERVICE"]`, без `org_id` — службовий юзер не належить жодній організації) і `expiresIn`.

Кожен зовнішній caller (Go-воркер, майбутній `document-service`) має власний службовий `User` з `platform_role = SERVICE` і без жодного `organization_member` — наприклад, `registry-monitor@service.internal` для Registry Monitor (засіяний у `V9__seed_registry_monitor_service_user.sql`). `password_hash` цього юзера навмисно **не** встановлюється міграцією (щоб секрет не потрапив у git-історію навіть хешованим) — його виставляють окремим операційним кроком у кожному оточенні, читаючи `SERVICE_SECRET` з Doppler/env. Поки секрет не виставлено, `password_hash IS NULL` і `POST /auth/service-token` для цього юзера гарантовано відмовляє (а не пускає з будь-яким паролем) — див. коментар у самій міграції.

Рейт-ліміти на цей ендпоінт налаштовані окремо (`RateLimitingService.checkServiceTokenLimits`, по `id` і по IP), як і для `/login`.
